### Medium Findings

#### 🟡 [M-1] Entire Supply Minted to Deployer (Centralization Risk)

**Description:**
The constructor mints 100% of the token supply to `msg.sender` with no vesting, lock, or distribution mechanism.

```solidity
uint256 scaledSupply = totalSupply_ * (10 ** uint256(decimals_));
_mint(msg.sender, scaledSupply);
```

The deployer holds the full circulating supply immediately after deployment.

**Impact:**
The deployer can dump the entire supply on the market, creating rug-pull / price-collapse risk for holders. Buyers should verify actual on-chain distribution and liquidity locks before trusting the token.

**Location:**
`CheesePadStandardToken` constructor.

**💡 Recommendation:**
> **Action Required:** Distribute supply across vesting contracts, liquidity pools, and locked allocations. Publicly document and lock team/deployer allocations, and provide verifiable liquidity-lock evidence.

### Low Findings

#### 🟢 [L-1] Unchecked Multiplication in Supply Scaling

**Description:**
The scaled supply is computed without an explicit sanity bound on `totalSupply_`:

```solidity
uint256 scaledSupply = totalSupply_ * (10 ** uint256(decimals_));
```

Under Solidity ^0.8.20 this reverts on overflow (safe), but an extremely large `totalSupply_` combined with 18 decimals could unexpectedly revert deployment, and there is no upper-bound validation to give a clear error.

**Impact:**
Poor UX / opaque revert on misconfigured deployment; no fund loss. Overflow itself is caught by the compiler's checked arithmetic.

**Location:**
`CheesePadStandardToken` constructor.

**💡 Recommendation:**
> **Action Required:** Add a `require` bounding `totalSupply_` to a sane maximum, or document expected input ranges to produce a clear revert reason.

#### 🟢 [L-2] Fee Forwarded via Low-Level Call in Constructor

**Description:**
The constructor forwards `msg.value` to an arbitrary `feeReceiver_` via a low-level call:

```solidity
(bool ok, ) = feeReceiver_.call{value: msg.value}("");
require(ok, "Fee transfer failed");
```

If `feeReceiver_` is a contract that reverts on receive, deployment fails. The call happens before `_mint`, so there is no reentrancy consequence for token balances, but the pattern places trust in the fee receiver.

**Impact:**
A malicious or misconfigured `feeReceiver_` can block deployment; no funds are locked because the whole transaction reverts. Low risk.

**Location:**
`CheesePadStandardToken` constructor.

**💡 Recommendation:**
> **Action Required:** Ensure `feeReceiver_` is a trusted, plain EOA or a well-tested receiving contract. Consider validating `feeAmount_ > 0` semantics if a zero fee should be permitted.

#### 🟢 [L-3] `payable` Constructor Allows Trapped Value When Fee Is Zero

**Description:**
The constructor is `payable` and requires `msg.value == feeAmount_`. When `feeAmount_` is 0, a zero-value call is enforced, which is correct, but if `feeReceiver_` is set to a contract that silently accepts 0-value calls the design still routes all native value externally—there is no path to recover accidentally attached value beyond the fee logic.

**Impact:**
Minimal; the strict `require(msg.value == feeAmount_)` prevents mismatched value. Informational hardening only.

**Location:**
`CheesePadStandardToken` constructor.

**💡 Recommendation:**
> **Action Required:** Confirm the fee flow matches business intent and document that no native value is retained by the token contract itself.
