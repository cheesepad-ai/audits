### Medium Findings

#### 🟡 [M-1] Unchecked supply scaling can silently overflow / revert deployment

**Description:**
The constructor computes the minted supply as:

```solidity
uint256 scaledSupply = totalSupply_ * (10 ** uint256(decimals_));
_mint(msg.sender, scaledSupply);
```

Because `decimals_` is caller-supplied (up to 18) and `totalSupply_` is unbounded, `10 ** decimals_` multiplied by a large `totalSupply_` can overflow `uint256`. Under Solidity ^0.8.20 this reverts (checked math), which is safe but wastes deployment gas/fee and gives no clear error. There is no validation that `totalSupply_` is non-zero either, so a token with zero supply can be deployed.

**Impact:**
A deployer passing extreme parameters will have the transaction revert after the fee external call executes (see L-1), potentially losing the forwarded fee context, or unintentionally deploy a zero-supply token. Not exploitable by third parties, but a usability/correctness concern.

**Location:**
`CheesePadStandardToken` constructor.

**💡 Recommendation:**
> **Action Required:** Add explicit bounds checks, e.g. `require(totalSupply_ > 0, "Zero supply")` and validate that `totalSupply_ <= type(uint256).max / (10 ** decimals_)` before multiplication to produce a clear revert reason.

#### 🟢 [L-1] External fee transfer occurs before state finalization in constructor

**Description:**
The constructor performs an external native-value call to an arbitrary `feeReceiver_` before minting:

```solidity
(bool ok, ) = feeReceiver_.call{value: msg.value}("");
require(ok, "Fee transfer failed");
_mint(msg.sender, scaledSupply);
```

While reentrancy into a contract mid-construction cannot corrupt the not-yet-deployed token (no external entry points exist yet), forwarding all `msg.value` via a raw low-level call to an unconstrained address is a pattern worth flagging. A malicious/reverting receiver can only cause the deployment to fail.

**Impact:**
Minimal — a bad `feeReceiver_` merely blocks deployment. No fund loss for third parties.

**Location:**
`CheesePadStandardToken` constructor.

**💡 Recommendation:**
> **Action Required:** Perform the fee transfer as the last constructor action (after `_mint`) to follow checks-effects-interactions ordering, and consider documenting the trusted nature of `feeReceiver_`.

#### 🟢 [L-2] `require(msg.value == feeAmount_)` makes `feeAmount_` redundant and error-prone

**Description:**
The `feeAmount_` parameter must exactly equal `msg.value`, otherwise the deployment reverts:

```solidity
require(msg.value == feeAmount_, "Invalid fee value");
```

Since the actual fee forwarded is `msg.value`, the separate `feeAmount_` argument provides no additional guarantee and only introduces a strict-equality failure mode (e.g. accidental overpayment reverts).

**Impact:**
Deployment convenience/robustness; not a security risk.

**Location:**
`CheesePadStandardToken` constructor.

**💡 Recommendation:**
> **Action Required:** Either remove `feeAmount_` and forward `msg.value` directly, or use `>=` with refund logic if enforcing a minimum fee is intended.

#### 🟢 [L-3] Wide pragma ranges in inherited files

**Description:**
The bundled OpenZeppelin interface files use permissive pragmas (`>=0.8.4`, `>=0.4.16`, `>=0.6.2`), while implementation files use `^0.8.20`. Compiling the concrete contract pins to a 0.8.x compiler, but wide floating pragmas are generally discouraged as they can allow compilation under unintended compiler versions in other contexts.

**Impact:**
No direct impact for this deployment; best-practice concern only.

**Location:**
Header pragmas across interface files.

**💡 Recommendation:**
> **Action Required:** Pin the deployment contract and all files to a fixed compiler version (e.g. `pragma solidity 0.8.24;`) for deterministic builds.
