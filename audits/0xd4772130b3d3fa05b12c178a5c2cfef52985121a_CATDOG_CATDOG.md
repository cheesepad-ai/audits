#### 🟠 [H-1] Sell path DoS: external BNB send to `taxWallet` can revert and block transfers

**Description:**
During sells, `_swapTokensForBNB()` is called before completing `_transfer()`. After swapping, the contract forwards BNB to `taxWallet` using a low-level `call`. If `taxWallet` is a contract whose `receive()`/`fallback` reverts (intentionally or by mistake, e.g., non-payable), the send reverts and the entire user transfer reverts, effectively bricking sells whenever auto-swap triggers.

```solidity
function _swapTokensForBNB(uint256 tokenAmount) internal lockSwap {
    ...
    try pancakeRouter.swapExactTokensForETHSupportingFeeOnTransferTokens(
        tokenAmount,
        0,
        path,
        address(this),
        block.timestamp + 300
    ) {
        uint256 bnbGained = address(this).balance - bnbBefore;
        if (bnbGained > 0) {
            (bool sent, ) = payable(taxWallet).call{value: bnbGained}("");
            if (!sent) revert BNBTransferFailed();  // Reverts user transfer path
            emit TaxSwappedAndSent(tokenAmount, bnbGained);
        }
    } catch {
        // Swap failure ignored
    }
}
```

**Impact:**
- Owner (or a compromised owner) can set `taxWallet` to a reverting contract to halt sells whenever swap triggers.
- Accidental misconfiguration (non-payable `taxWallet`) can unintentionally DoS selling.

Exploit scenario: Owner sets `taxWallet` to a contract that reverts on receiving BNB. Any sell that triggers auto-swap reverts, freezing market exits.

**Location:**
`_swapTokensForBNB()` BNB forward to `taxWallet`.

**💡 Recommendation:**
> **Action Required:** Decouple external payout from the transfer path.
> 1. Do not revert if `taxWallet` send fails; retain BNB in contract and allow `rescueBNB()` to withdraw later.
> 2. Prefer a pull model: accumulate BNB; owner/tax wallet withdraws via separate non-reentrant function.
> 3. Strongly recommend enforcing `taxWallet` to be an EOA, or add a configurable gas-limited `sendValue`-like pattern and non-reverting fallback.

#### 🟡 [M-1] Reentrancy surface from external `taxWallet` call during `_transfer`

**Description:**
When selling, `_transfer()` calls `_swapTokensForBNB()` which performs an external `call` to `taxWallet` before finishing the transfer. Although `_inSwap` blocks nested swaps, the external call allows `taxWallet` (if a contract) to reenter ERC20 functions (e.g., `transfer()`, `approve()`) mid-execution, potentially interacting with evolving state.

```solidity
if (
    swapEnabled &&
    !_inSwap &&
    isAMMPair[to] &&
    !isExcludedFromFee[from]
) {
    uint256 contractBalance = _balances[address(this)];
    if (contractBalance >= swapThreshold) {
        uint256 toSwap = contractBalance > maxSwapAmount ? maxSwapAmount : contractBalance;
        _swapTokensForBNB(toSwap); // external call -> reentrancy window
    }
}
```

**Impact:**
- Unexpected nested ERC20 interactions while original `_transfer` is in progress.
- Combined with owner privileges, can enable mid-tx parameter changes (e.g., taxes, exclusions). While owner can do this anyway, reentrancy increases complexity and attack surface.

**Location:**
`_transfer()` sell branch before balance updates.

**💡 Recommendation:**
> **Action Required:**
> - Ensure `taxWallet` is an EOA, or
> - Avoid external value transfers inside `_transfer()`; move BNB payout to a separate function, or
> - Add a broader reentrancy guard for user-facing paths that can be safely guarded (avoid breaking ERC20 composability), and document EOA requirement for `taxWallet`.

#### 🟢 [L-4] Standard ERC20 approve race condition

**Description:**
The `approve()` pattern is susceptible to the well-known race where a spender can front-run allowance changes.

```solidity
function approve(address spender, uint256 amount) external override returns (bool) {
    _approve(_msgSender(), spender, amount);
    return true;
}
```

**Impact:**
- Spender may use both old and new allowance in a race scenario.

**Location:**
`approve()`.

**💡 Recommendation:**
> **Action Required:**
> - Encourage use of `increaseAllowance()`/`decreaseAllowance()` patterns in interfaces or require setting allowance to 0 before non-zero updates (doc-only if changing interface is undesired).
