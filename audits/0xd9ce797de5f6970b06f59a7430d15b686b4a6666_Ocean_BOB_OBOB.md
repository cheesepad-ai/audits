#### 🟠 [H-1] Owner-controlled payout wallets can induce DoS during swaps

**Description:**
`swapAndSend()` performs external calls to `marketingWallet` and `devWallet` via `Address.sendValue`. If either wallet is a contract that reverts on receive (or deliberately reverts), every transfer that attempts to trigger `swapAndSend()` will revert, causing a denial of service for users when `canSwap` conditions are met.

```solidity
function swapAndSend(uint256 tokens) private {
    uint256 initialBalance = address(this).balance;
    swapTokensForBNB(tokens);
    uint256 received = address(this).balance - initialBalance;
    if (received > 0) {
        uint256 marketingShare = (received * 60) / 100;
        payable(marketingWallet).sendValue(marketingShare);
        payable(devWallet).sendValue(received - marketingShare);
    }
}
```

**Impact:**
- Transfers that attempt to trigger swaps can be bricked by setting `marketingWallet`/`devWallet` to a reverting contract.
- Owner can unintentionally or maliciously disrupt trading for non-excluded users.

**Location:**
`swapAndSend()`; called from `_transfer()` when `canSwap` is true.

**💡 Recommendation:**
> **Action Required:**
> 1. Add a non-reverting payout mechanism (e.g., wrap sends in try/catch, or accumulate unpaid balances to claim-later).
> 2. Enforce `marketingWallet`/`devWallet` to be EOAs and add a sanity check before updating them.
> 3. Emit events and allow recovery to a safe address if payout fails.
> - Alternative: Use pull-based claims instead of push payments.

**Impact:**

- Conversely, intended values require unintuitive scaling by the caller, increasing operational risk.

**Location:**

**💡 Recommendation:**
