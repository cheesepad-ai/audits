### Medium Findings

#### 🟡 [M-1] Unchecked Supply Scaling Can Overflow in Constructor

**Description:**
The constructor computes the scaled supply without any bounds check on `totalSupply_`:

```solidity
uint256 scaledSupply = totalSupply_ * (10 ** uint256(decimals_));
_mint(msg.sender, scaledSupply);
```

While Solidity 0.8.x reverts on overflow, a caller supplying a large `totalSupply_` combined with `decimals_ = 18` can cause the multiplication to revert, preventing deployment. More importantly, no minimum or maximum supply invariant is enforced, and `totalSupply_` of `0` yields a token with zero supply and no way to ever mint more (no exposed mint function).

**Impact:**
Deployment failures from overflow revert, or permanent creation of a zero-supply, unusable token. No mid-transaction fund loss, but a bricked deployment is possible.

**Location:**
`CheesePadStandardToken` constructor.

**💡 Recommendation:**
> **Action Required:** Add sanity bounds, e.g. `require(totalSupply_ > 0, "zero supply")` and an upper bound on `totalSupply_` to keep `scaledSupply` within a sane range. Document the expected raw (un-scaled) supply units clearly.

### Low Findings

#### 🟢 [L-1] External Call (Fee Transfer) in Constructor Before State Finalization

**Description:**
The constructor sends native currency to an arbitrary `feeReceiver_` via a low-level call before minting:

```solidity
(bool ok, ) = feeReceiver_.call{value: msg.value}("");
require(ok, "Fee transfer failed");
_mint(msg.sender, scaledSupply);
```

The recipient is fully controlled by the deployer, and no token state exists to manipulate during construction, so reentrancy is not exploitable here. However, forwarding all `msg.value` to an externally chosen address is a code smell and can revert deployment if the receiver rejects funds.

**Impact:**
Low. A malicious/faulty `feeReceiver_` can only cause the deployer's own deployment to revert.

**Location:**
`CheesePadStandardToken` constructor, fee-transfer block.

**💡 Recommendation:**
> **Action Required:** Consider using a fixed, trusted fee receiver or a pull-payment pattern. At minimum, follow checks-effects-interactions by performing the external call last.

#### 🟢 [L-2] Payable Constructor Requires Exact Fee Match

**Description:**
`require(msg.value == feeAmount_, "Invalid fee value")` requires the caller to supply exactly `feeAmount_`. Since `feeAmount_` is a caller-supplied argument, the deployer sets both the fee and the value they send, making the check trivially satisfiable and providing no real fee enforcement against the deployer.

```solidity
require(msg.value == feeAmount_, "Invalid fee value");
```

**Impact:**
The fee mechanism offers no protocol-level guarantee; a deployer can pass `feeAmount_ = 0` and send nothing. Purely informational unless enforced by an external factory.

**Location:**
`CheesePadStandardToken` constructor.

**💡 Recommendation:**
> **Action Required:** If a mandatory fee is intended, hardcode `feeAmount_` and `feeReceiver_` as constants or enforce them via a trusted factory contract rather than trusting caller-supplied values.

#### 🟢 [L-3] No Event Emitted for Fee Payment

**Description:**
The constructor forwards funds to `feeReceiver_` but emits no event recording the fee amount or recipient, reducing off-chain traceability of the deployment fee.

**Impact:**
Minor observability gap; harder to index/audit fee flows.

**Location:**
`CheesePadStandardToken` constructor.

**💡 Recommendation:**
> **Action Required:** Emit a dedicated event (e.g. `FeePaid(feeReceiver_, msg.value)`) after a successful fee transfer.
