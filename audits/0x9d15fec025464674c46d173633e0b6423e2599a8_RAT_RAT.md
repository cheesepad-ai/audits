### Medium Findings

#### 🟡 [M-1] Unchecked supply scaling can revert or produce unintended supply

**Description:**
The constructor computes `scaledSupply = totalSupply_ * (10 ** uint256(decimals_))` without bounding `totalSupply_`. While Solidity ^0.8.20 protects against silent overflow (a too-large product reverts), there is no upper-bound validation. A deployer supplying a very large `totalSupply_` with high `decimals_` will cause the deployment to revert, and there is no sanity range on the resulting economic supply.

```solidity
uint256 scaledSupply = totalSupply_ * (10 ** uint256(decimals_));
_mint(msg.sender, scaledSupply);
```

**Impact:**
Deployment-time revert (wasted gas / failed launch) for extreme inputs; no runtime exploit. Supply parameters are entirely trusted to the deployer with no invariant guarding against a mistaken value.

**Location:**
`CheesePadStandardToken` constructor.

**💡 Recommendation:**
> **Action Required:** Document the expected range of `totalSupply_`, and optionally add an explicit upper-bound `require` (e.g. cap `scaledSupply` to a sane maximum) to fail fast with a clear error instead of an arithmetic revert.

### Low Findings

#### 🟢 [L-1] Fee transfer via low-level call before minting (reentrancy surface)

**Description:**
The constructor performs an external `call` to `feeReceiver_` forwarding `msg.value` before `_mint`. Since this occurs in the constructor and no persistent contract state is read after the call except minting to `msg.sender`, exploitation is not practical. However, executing an untrusted external call before completing all initialization is a code-smell.

```solidity
(bool ok, ) = feeReceiver_.call{value: msg.value}("");
require(ok, "Fee transfer failed");
_mint(msg.sender, scaledSupply);
```

**Impact:**
No practical reentrancy exploit (constructor context, no reentrant entrypoints, no state to corrupt), but violates checks-effects-interactions ordering.

**Location:**
`CheesePadStandardToken` constructor.

**💡 Recommendation:**
> **Action Required:** Move `_mint` before the fee transfer, or perform the fee transfer last after all effects, to follow checks-effects-interactions.

#### 🟢 [L-2] No zero-supply guard

**Description:**
The constructor does not validate `totalSupply_ > 0`. A deployment with `totalSupply_ == 0` produces a token with no supply and no way to mint more (no mint function), rendering it permanently useless.

**Impact:**
Non-functional token if deployed with zero supply; no on-chain remediation possible.

**Location:**
`CheesePadStandardToken` constructor.

**💡 Recommendation:**
> **Action Required:** Add `require(totalSupply_ > 0, "Zero supply")` if a non-zero supply is always intended.

---

#### 🟢 [L-3] Standard ERC-20 approve front-running race

**Description:**
The inherited `approve` allows the classic allowance race condition where a spender can spend both the old and new allowance via transaction ordering. This is an inherent ERC-20 limitation and is acknowledged in the OpenZeppelin comments.

**Impact:**
A spender may spend more than intended when an allowance is changed from a non-zero value to another non-zero value.

**Location:**
`ERC20.approve` / `_approve`.

**💡 Recommendation:**
> **Action Required:** Advise integrators/users to set allowance to 0 before setting a new non-zero value, or use `safeIncreaseAllowance` / `safeDecreaseAllowance` patterns off-chain.
