### High Findings

#### 🟠 [H-1] Unprotected `withdrawStuckBNB` allows anyone to force-drain contract BNB to marketing wallet

**Description:**
`withdrawStuckBNB` has no access control. Any external caller can invoke it, sending the entire contract BNB balance to `marketingAddress`.

```solidity
function withdrawStuckBNB() external {
    bool success;
    (success, ) = address(marketingAddress).call{
        value: address(this).balance
    }("");
}
```

While funds only go to `marketingAddress` (not the caller), an attacker can grief the tax mechanism by prematurely draining accumulated BNB before intended distribution splits occur, and the ignored `success` return value can silently fail.

**Impact:**
Any user can trigger BNB transfers out of the contract at any time, bypassing the 60/40 marketing/dev split logic in `convertTaxes`. All BNB is forced to marketing, disadvantaging the dev address. Ignored return value can leave the transaction misleadingly successful.

**Location:**
`withdrawStuckBNB()`

**💡 Recommendation:**
> **Action Required:** Add an access-control modifier (e.g. `onlyOwner` or restrict to `marketingAddress`/`devAddress`), and `require(success)` on the call. Since ownership is renounced, restrict it to the marketing/dev addresses.

### Medium Findings

#### 🟡 [M-1] Swap-back uses `amountOutMin = 0`, exposing tax swaps to sandwich/MEV attacks

**Description:**
`swapTokensForETH` passes `0` as the minimum output amount when swapping accumulated tax tokens for BNB.

```solidity
    tokenAmt, 0, path, address(this), block.timestamp

```

MEV bots can sandwich these swaps, extracting value from every tax conversion.

**Impact:**
Loss of tax revenue to MEV bots on every swap-back, reducing BNB received by marketing and dev wallets. Frequent for high-volume trading pairs.

**Location:**
`swapTokensForETH()` / `convertTaxes()`

**💡 Recommendation:**
> **Action Required:** Compute a sensible `amountOutMin` via an oracle or slippage tolerance, or limit swap-back frequency and size. Note ownership is renounced, so this cannot be patched—only future redeploys.

#### 🟡 [M-2] `rescueTokens` can drain the contract's own TEKE tax tokens

**Description:**
`rescueTokens` allows `marketingAddress` to transfer any ERC20 held by the contract, including the contract's own accumulated TEKE tax tokens, to the marketing wallet.

```solidity
function rescueTokens(address _token) external {
    require(msg.sender == marketingAddress, "Not marketing");
    ...
    SafeERC20.safeTransfer(IERC20(_token), address(marketingAddress), _contractBalance);
}
```

There is no exclusion of `address(this)`, so pending tax tokens can be pulled directly rather than swapped, centralizing control in the marketing wallet.

**Impact:**
The marketing wallet can withdraw the token's own tax reserves as raw tokens at any time, bypassing the intended swap-and-split distribution. This is a centralization/trust concern.

**Location:**
`rescueTokens()`

**💡 Recommendation:**
> **Action Required:** Disallow rescuing `address(this)` tokens (`require(_token != address(this))`), or clearly document this privilege for holders.

#### 🟡 [M-3] Fixed low gas stipend on BNB transfers can silently fail for contract recipients

**Description:**
`convertTaxes` sends BNB to marketing and dev addresses using a hardcoded `gas: 35000` stipend and ignores the `success` result.

```solidity
(success, ) = marketingAddress.call{value: marketingShare, gas: 35000}("");
```

If either address is a contract with a receive/fallback that consumes more than 35000 gas, the transfer silently fails and funds accumulate in the contract, only recoverable via the flawed `withdrawStuckBNB`.

**Impact:**
Tax BNB can become stuck if recipient addresses are contracts (multisigs, proxies). Failure is silent because `success` is unchecked.

**Location:**
`convertTaxes()`

**💡 Recommendation:**
> **Action Required:** Remove the fixed gas cap or raise it, and handle/require the `success` value. Prefer a pull-payment pattern for contract recipients.
