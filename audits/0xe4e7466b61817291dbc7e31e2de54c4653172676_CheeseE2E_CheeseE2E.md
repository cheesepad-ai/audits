### Medium Findings

#### 🟡 [M-1] Unchecked supply scaling can silently overflow

**Description:**
The constructor computes the scaled supply with a raw multiplication in Solidity 0.8 checked arithmetic:

```solidity
uint256 scaledSupply = totalSupply_ * (10 ** uint256(decimals_));
_mint(msg.sender, scaledSupply);
```

While Solidity ≥0.8 reverts on overflow (so no silent wrap occurs), there is no upper bound validation on `totalSupply_`. A caller supplying a very large `totalSupply_` combined with `decimals_ = 18` can either revert deployment (griefing / wasted gas) or, if just below the overflow threshold, mint an absurd supply that breaks downstream integrations, price feeds, and AMM math. Since this is a factory-style/mock token where parameters are user-supplied, unbounded input should be validated.

**Impact:**
Deployments with pathological parameters either revert unexpectedly or produce an economically meaningless supply. No fund loss, but a correctness and usability risk for any automated deployment pipeline.

**Location:**
`CheesePadStandardToken` constructor — `scaledSupply` computation.

**💡 Recommendation:**
> **Action Required:** Add a sanity bound on `totalSupply_` (e.g., `require(totalSupply_ <= MAX_SUPPLY_UNSCALED, "Supply too large")`) so overflow-prone inputs are rejected with a clear message rather than a generic arithmetic revert, and to prevent economically nonsensical supplies.

### Low Findings

#### 🟢 [L-1] Fee sent via low-level call to arbitrary receiver in constructor

**Description:**
The constructor forwards `msg.value` to a caller-controlled address using a low-level `call`:

```solidity
(bool ok, ) = feeReceiver_.call{value: msg.value}("");
require(ok, "Fee transfer failed");
```

The external call is made before `_mint`. Although state changes after the call are limited to minting (which is internal and follows checks-effects reasonably), calling an arbitrary address during construction gives that address execution control. In this specific contract the reentrancy surface is negligible because minting to `msg.sender` is idempotent within a single constructor run, but the pattern of an unbounded external call to a user-supplied address remains a latent risk if the contract is extended.

**Impact:**
Low. A malicious `feeReceiver_` cannot meaningfully re-enter the current logic, but the pattern is fragile against future modifications.

**Location:**
`CheesePadStandardToken` constructor — fee transfer.

**💡 Recommendation:**
> **Action Required:** Perform all state-affecting operations (including `_mint`) before the external fee transfer, or move the fee logic to the end of the constructor, adhering strictly to checks-effects-interactions.

#### 🟢 [L-2] Fee amount is redundant and can trap value

**Description:**
The constructor requires `msg.value == feeAmount_` and then forwards the entire `msg.value` to the receiver. The `feeAmount_` parameter is fully redundant with `msg.value` and adds no protection — it only introduces a way for deployment to revert on mismatch. If `feeReceiver_` is a contract that consumes less than the full amount or the forwarding logic changed, any residual value could become locked, since the contract holds no withdrawal mechanism.

**Impact:**
Low. Redundant parameter increases misconfiguration risk; contract has no `receive`/withdraw path for stranded funds.

**Location:**
`CheesePadStandardToken` constructor — `require(msg.value == feeAmount_, ...)`.

**💡 Recommendation:**
> **Action Required:** Drop the `feeAmount_` parameter and simply forward `msg.value`, or if a fixed fee is required, validate against a constant. Ensure no ETH can be stranded in the contract.
